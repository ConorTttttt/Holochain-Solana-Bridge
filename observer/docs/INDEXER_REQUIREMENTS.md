## What S0 actually verifies and what it does not

`observeRpc` compares the provider's `getGenesisHash` to the supplied trusted genesis, then asks `getMultipleAccounts` at `commitment: 'finalized'` for receipt, config, vault and mint in one response. It rejects wrong account owners, noncanonical addresses, substituted PDAs, wrong stored bumps, invalid Anchor discriminators/lengths, malformed base64, noncanonical booleans/COptions, wrong mint/scope/vault/config, wrong SPL authority or token program, frozen/native/delegated/closeable vaults, freezable/uninitialized mints, zero recipient/amount, inconsistent supply and aggregate vault liabilities. All u64 values are exact decimal strings.

A **provider-controlled account view is not cryptographic consensus evidence**. The `finalizedSlot` is RPC-asserted; pure `verifySnapshot` cannot independently prove a commitment. Program ID, genesis, mint and Holochain scope MUST be pinned by a separately verified deployment manifest and cannot safely be selected by an adversarial caller. `getMultipleAccounts` is a coherent *reported* bank snapshot, not evidence that a successful deposit transaction created it. `minContextSlot` is only a slot floor, not a historical slot pin.

Comparing two RPC reports is not proof of independence. `reconcileObservations` fails closed when receipt bytes/state differ, or when a **same-slot** config/vault/mint digest differs. Different finalized slots may have different vault balances; the output explicitly says `agreement: 'receipt_bytes_only'` in that case. Two providers may collude, share upstream infrastructure or provide false finalized slots. A deposit can be **refunded after any observation**.

## Read-only evidence schema for RAVE / SEC / CI

`kind: 'solana-receipt-observation-v1'`; `id = genesisHash:program:receiptAddress`; `source`; `genesisHash`; `finalizedSlot`; `commitmentRequested: 'finalized'`; `program`, `receiptAddress`, `configAddress`, `vaultAddress`, `mint`; `depositor`, `recipientCore`, `holochainScope`, `depositNonce`, `amountBaseUnits`; `activeVaultBaseUnits`, `activeLiabilitiesBaseUnits`, `mintSupplyBaseUnits`; `receiptDigest`, `configDigest`, `vaultDigest`, `mintDigest` (SHA-256 of raw account bytes); `configBump`, `receiptBump`; `refunded`; `state: 'refunded' | 'active_refundable'`; **`transactionVerified: false`**, **`evidenceTrust: 'untrusted_rpc_snapshot'`**, **`creditEligible: false`**. Two-provider reconciliation also reports `checkedBy`, `providerFinalizedSlots`, and `agreement`. These are unauthenticated claims from RPC; no field is a Solana inclusion/consensus proof or an authorization. All downstream consumers MUST treat this data as hostile.

A future transaction-evidence extension should attach `evidenceSchemaVersion`, verified creation `signature`, `slot`, `blockhash`, transaction `version`, outer and inner instruction indices/CPI path, program/instruction/account hashes, `meta.err === null`, exact instruction parameters, matched pre/post token deltas, PDA/receipt linkage, creation/refund lifecycle, independently compared source blockhashes, verification-policy version, and persistent replay ledger identity. It must remain observation-only and `creditEligible: false` until separately authorized economic security gates are met.

## Requirements for S1/S2 finalized transaction indexer

1. **Gap-free backfill and finalized tail:** bootstrap from trusted deployment/start slot; enumerate finalized slot ranges and read full blocks via `getBlock` (`commitment: 'finalized'`, `transactionDetails: 'full'`, numeric `maxSupportedTransactionVersion: 1`). Check every expected completed slot, distinguish skipped slots from missing/pruned/unavailable data, archive blockhash and slot. `getSignaturesForAddress` is paginated (up to 1000/page) and is useful for cross-checking, but is not an independently complete history. Never advance a checkpoint past an unexamined block.
2. **Explicit legacy / v0 / v1 support:** pass numeric `maxSupportedTransactionVersion: 1` in `getBlock` and `getTransaction`. Decode legacy, v0 including Address Lookup Tables and resolved `meta.loadedAddresses`, and v1 with inline keys and `transactionConfig` (no ALT). Refuse unsupported versions, missing metadata or unresolved account keys. Prefer base64/raw decoding with pinned, v1-aware Solana Kit 8+; do not accept server-parsed `jsonParsed` as equivalent byte evidence. v1 resource limits cannot be inferred from absent ComputeBudget instructions.
3. **Verify creating transaction:** require `meta.err === null`, exact deployed program/instruction discriminator, signers, expected accounts and canonical PDAs, approved classic SPL mint/token program, exact u64 deposit parameters, successful checked SPL transfer and resulting receipt and custody delta. A log/event alone, a final balance or a preexisting receipt is insufficient. One transaction can contain multiple deposits, including CPI: index **instruction occurrences/unique receipts**, not just signatures. Refunded receipts must be tracked through corresponding successful refund transitions.
4. **Crash-safe exactly-once:** unique durable key `(genesis, program, receiptAddress)` plus creation `(signature, instruction_path)`; persist accepted evidence and any state transitions *atomically with* the finalized block cursor and blockhash. Replayed identical events are idempotent, conflicting duplicates halt; a refunded identity is never recycled. Exercise crashes before and after each DB write/commit and rebuild from history. In-memory `assertUniqueObservations` is only a batch guard and is **not** durable replay protection.
5. **Disagreement and historical availability:** compare genesis, finalized slot/hash, full transaction bytes/account outcomes and receipt state across independent RPC operators; do not resolve conflicting reports by majority assumption. Halt/quarantine on divergence, timeouts, pruning, pagination discontinuities, unsupported formats, nil block responses and lagging sources. Record provenance and errors without exposing API keys; never silently treat missing history as zero deposits.
6. **Holochain trust boundary:** no spendable Holochain credit, signing or withdrawals. Solana program upgrade authority, verified deployed bytecode, collateral nonrefundability, source attestor/consensus proofs and Holochain cross-fork/recovery/replay semantics all require separate security gates and independent review.
